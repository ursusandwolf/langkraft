## 1. Вердикт и область проверки

**Вердикт:** кодовая база Web MVP в целом пригодна для передачи коллегам с документированными ограничениями. **Для публичного размещения backend есть блокирующее ограничение P1:** одновременность импорта ограничена, но объём загрузок, расход диска и срок хранения не ограничены. **Для надёжной долговременной работы локального Web-хранилища остаются P2-дефекты**, в том числе непривязанное аудио и недостаточное восстановление после внезапного закрытия вкладки. Упомянутые ниже находки, кроме специально обозначенных независимых SQL-проверок, **получены статическим анализом; фактическое браузерное/серверное воспроизведение в этой среде не проводилось**.

Проверены `backend`, `shared` (репозитории, use case, Web/JVM storage, схема и миграция, плеер), `webApp`, Gradle/CI, README, документация. Android просмотрен только статически: он отключён по умолчанию. Тесты и browser-test tools **намеренно отсутствуют в архиве**; это не дефект. Ни количество, ни результат тестов полного репозитория независимо не подтверждены.

## 2. Находки по убыванию приоритета

### LK-01 — P1 (публичный backend): один или несколько импортов могут исчерпать CPU/диск

- **Участки:** `backend/src/main/kotlin/com/langkraft/backend/YouTubeIngestionService.kt:29,34–41,47–55,90–92`; `backend/src/main/kotlin/com/langkraft/backend/YtDlpRunner.kt:18–20,34–35`; `backend/src/main/kotlin/com/langkraft/backend/Application.kt:25,38–41,51–54`.
- **Условие:** публичный сервер принимает импорты от неограниченного числа клиентов, видео могут быть очень длинными или большими; завершённые скачивания остаются в `DOWNLOADS_DIR` без срока хранения.
- **Цепочка и доказательство:** `POST /api/ingest` → `ingest()` с `Semaphore(maxConcurrentImports)` → `yt-dlp --extract-audio ...` с временным лимитом 600 секунд. `tryAcquire()` действительно **ограничивает число одновременно запущенных загрузок** (по умолчанию двумя) и сразу возвращает 503 при перегрузке; `finally` освобождает слот. Но ни размер одного файла, ни суммарная квота, ни количество сохранённых успешных импортов не ограничены. При успехе вызывающего удаления файлов нет; `deleteFiles()` вызывается только при исключении/отмене. Кроме готового `.opus`, остаются скачанные сопутствующие файлы.
- **Ущерб:** исчерпание дискового пространства, деградация/отказ HTTP-сервиса. Для доверенного запуска на локальном компьютере **P2/ограничение эксплуатации**, не самостоятельный P1 на merge.
- **Минимальное исправление:** задать максимально допустимые размер и продолжительность видео (проверка метаданных до скачивания + жёсткий контроль фактических байтов/времени), квоту каталога и политику удаления/TTL; до публичного доступа добавить контроль пользователей/запросов или оставить backend только за доверенным доступом. Сохранять существующую семафорную границу.
- **Подтверждающая проверка:** тестовый runner с двумя занятыми слотами должен возвращать 503 для третьего запроса; серия последовательных успешных импортов должна упираться в общий бюджет, чрезмерный файл — прерываться с очисткой, TTL — удалять невостребованные файлы.
- **Классификация:** статически подтверждённое отсутствие границ; ограничение ранее известно и описано в инструкции/README.

### LK-02 — P2: опубликованное аудио теряется из логической библиотеки при финальном сбое

- **Участки:** `shared/src/commonMain/kotlin/com/langkraft/domain/usecase/IngestContentUseCase.kt:16–32`; `shared/src/jsMain/kotlin/com/langkraft/data/audio/IndexedDbAudioStorage.kt:21–40`; `shared/src/jsMain/storage/index.js:117–131`; `shared/src/jvmMain/kotlin/com/langkraft/data/audio/FileAudioStorage.kt:46–53`; `shared/src/commonMain/kotlin/com/langkraft/data/audio/AudioStorage.kt:5–8`.
- **Условие:** `downloadAudio()` успешно вернул `indexeddb-audio:...` или путь файла, после чего второй `saveContent(updatedContent)` завершился ошибкой, например при сбое SQLite, либо произошла отмена в промежутке после публикации аудио.
- **Цепочка и доказательство:** первый `saveContent(remoteContent)` сохраняет контент с `localAudioPath = null` → `downloadAudio()` **публикует** аудио → второй `saveContent()` привязывает ссылку. Компенсирующей очистки при неуспехе последнего шага нет. `AudioStorage` предоставляет только `store`, а `abortAudio()` вызывается лишь внутри `store` до его успешного возврата.
- **Ущерб:** неограниченное накопление уже завершённых, но недоступных аудиозаписей; ошибка импорта при наличии расхода квоты.
- **Минимальное исправление:** расширить абстракцию хранения операцией удаления по выданному location и вызвать её при исключении/отмене после публикации; либо ввести состояние pending/commit с периодическим reconciliation. При неуспешном *скачивании* текущая политика сохранения удалённых метаданных может остаться без изменений.
- **Подтверждающая проверка:** подменить вторую запись контента исключением после успешного `store` и проверить отсутствие объектов без ссылок; отдельно отменить между `store` и второй записью, проверить повторное открытие хранилища.
- **Классификация:** статический вывод; ранее описанная, всё ещё открытая находка.

### LK-03 — P2: внезапно закрытая вкладка оставляет незавершённые аудиозаписи

- **Участки:** `shared/src/jsMain/storage/index.js:53–71,91–115,117–142`; `shared/src/jsMain/kotlin/com/langkraft/data/audio/IndexedDbAudioStorage.kt:21–40`; `webApp/src/jsMain/kotlin/com/langkraft/web/Main.kt:79–85,162–177`.
- **Условие:** пользователь закрывает/убивает вкладку, браузер аварийно завершается или устройство выключается **после** `beginAudio()` и нескольких `appendAudio()`, но до `commitAudio()`/`abortAudio()`.
- **Цепочка и доказательство:** `beginAudio()` создаёт долговечную запись `complete: false`; каждый `appendAudio()` коммитит чанки отдельной транзакцией. При обработанной ошибке Kotlin `catch` вызывает `abortAudio()`. При прекращении исполнения страницы `catch` не выполняется; `openAudioDatabase()` при следующем запуске только открывает БД — восстановления или удаления `complete: false` нет. `readAudioBlob()` специально скрывает эти записи, но чанки занимают место.
- **Ущерб:** тихое накопление частичных объектов вплоть до ошибки квоты браузера; особенно актуально при многократном импорте больших роликов.
- **Минимальное исправление:** хранить `startedAt`/`updatedAt` у manifest и выполнять безопасную уборку незавершённых загрузок при старте и/или после TTL. Не удалять активную загрузку другой вкладки: нужен lease/owner или консервативный срок.
- **Подтверждающая проверка:** в Chromium начать загрузку, сохранить 2–3 чанка, принудительно завершить страницу/worker **без вызова abort**, открыть страницу заново и проверить, что очистка удаляет manifest и все чанки, не затрагивая завершённые объекты. Повторить с двумя активными вкладками.
- **Классификация:** статически подтверждённая неполнота recovery; новый сценарий относительно документа `docs/CODE_REVIEW_2026-10-21.md`.

### LK-04 — P2: состояние библиотеки устаревает между вкладками

- **Участки:** `shared/src/jsMain/kotlin/com/langkraft/data/database/BrowserSqlDriver.kt:21–23,90–102`; `shared/src/commonMain/kotlin/com/langkraft/data/repository/SqlDelightContentRepository.kt:28–40`; `webApp/src/jsMain/kotlin/com/langkraft/web/Main.kt:112–117`.
- **Условие:** библиотека открыта одновременно в вкладках A и B одного origin; A сохраняет новое видео или обновляет его субтитры.
- **Цепочка и доказательство:** SQLDelight listener registry — `private val listeners` **внутри экземпляра driver**. `notifyListeners()` вызывает только свои callbacks, и каждый новый вызов `createWebDatabase()` создаёт собственный worker и driver. `getAllContent().asFlow()` другой вкладки сам не получает событие; нет `BroadcastChannel`, `storage` event или принудительной ревалидации библиотеки.
- **Ущерб:** устаревшие списки и субтитры в B до перезагрузки/нового запроса. Межвкладочные конкурирующие записи — **отдельная гипотеза**, требующая браузерного тестирования; mutex репозиториев защищает только один driver.
- **Минимальное исправление:** после успешного commit рассылать сигнал изменения по `BroadcastChannel` или явно поддерживать только одну активную вкладку; подписчик должен перечитать SQL-запросы. Проверить, как VFS ведёт себя при двух одновременных соединениях.
- **Подтверждающая проверка:** две вкладки в одном профиле; A делает импорт, B без reload обновляет библиотеку. Дополнительно выполнить параллельную запись разных объектов и переоткрытие БД.
- **Классификация:** статический вывод; ранее известная находка, не исправлена.

### LK-05 — P2: при утрате файла из IndexedDB плеер не использует удалённое аудио

- **Участки:** `shared/src/commonMain/kotlin/com/langkraft/ui/player/PlayerViewModel.kt:145–165`; `shared/src/jsMain/kotlin/com/langkraft/audio/AudioPlayerImpl.kt:62–90`; `shared/src/jsMain/storage/index.js:144–166`; `shared/src/commonMain/kotlin/com/langkraft/ui/player/ImmersionPlayerView.kt:52–55`.
- **Условие:** запись SQLite сохранила `localAudioPath = indexeddb-audio:...`, но соответствующая запись аудиохранилища исчезла, повреждена или не может быть прочитана. Удалённый `audioUrl` по-прежнему доступен.
- **Цепочка и доказательство:** `PlayerViewModel` всегда вызывает `audioPlayer.load(content.localAudioPath ?: content.audioUrl)`. Если локальная ссылка непустая, remote URL не используется. `readAudioBlob()` выбрасывает ошибку при отсутствии/неполноте объекта; `AudioPlayerImpl` передаёт её в `error`, но не возвращает управление модели для повторения с `content.audioUrl`. Кнопка `RETRY` снова вызывает тот же `loadContent()` с тем же `localAudioPath`.
- **Ущерб:** видео становится невоспроизводимым, хотя сетевой ресурс может быть доступен, и повторные нажатия `RETRY` ничего не меняют.
- **Минимальное исправление:** дать слою плеера явный сигнал «локальный media asset недоступен» и один раз пробовать `audioUrl` (или очищать устаревшую ссылку только после проверки); другие ошибки, особенно autoplay-policy, не должны молча переключаться на сеть. Предусмотреть ручное «Играть по сети/скачать заново».
- **Подтверждающая проверка:** импорт с локальным `indexeddb-audio` → удалить **только** соответствующие manifest/chunks → сохранить SQLite и подменить HTTP media fixture → открыть плеер и проверить воспроизведение по remote без циклического retry.
- **Классификация:** статически подтверждённый сбой восстановления; возможность частичной потери хранилища зависит от браузера/пользовательских действий.

### LK-06 — P3: неверный ответ HTTP 2xx принимается за аудиофайл

- **Участки:** `shared/src/commonMain/kotlin/com/langkraft/data/remote/ContentApi.kt:49–58`; `shared/src/jsMain/storage/index.js:117–131`; `shared/src/jvmMain/kotlin/com/langkraft/data/audio/FileAudioStorage.kt:31–49`.
- **Условие:** reverse proxy неверно направляет `/api/media/...` на HTML-страницу приложения либо возвращает другой непустой успешный ответ 2xx вместо Opus.
- **Цепочка и доказательство:** `checkResponse()` проверяет только `status.isSuccess()`; содержимое передаётся в `storage.store(...)`. Хранилища проверяют непустой объём/длину, но не media type и не сигнатуру контейнера. Таким образом `200 text/html` с корректным Content-Length будет опубликован как аудио, а ссылка попадёт в SQLite.
- **Ущерб:** интерфейс сообщает, что аудио сохранено, но воспроизведение не удаётся; сложно выявляемая ошибка развёртывания.
- **Минимальное исправление:** убедиться, что ответ ожидаемого типа (`audio/ogg`, допустимые Opus media types), отвергать явное `text/html`; при необходимости проверять magic `OggS` перед публикацией. Не опираться только на MIME при возможных особенностях сервера.
- **Подтверждающая проверка:** mock GET медиа возвращает `200 text/html` с непустым телом; импорт должен завершиться ошибкой скачивания без публикации локального аудио. Валидный Opus должен продолжить сохраняться.
- **Классификация:** статический сценарий, зависим от ошибочного upstream; не блокирует локальный MVP.

## 3. Сопоставление с прежним отчётом

Документ `docs/CODE_REVIEW_2026-10-21.md` основан на более раннем состоянии. Для снимка `397d007` проверено:

1. **Старый пункт 1 (неограниченное число параллельных импортов): исправлен в своей исходной формулировке.** В `YouTubeIngestionService.kt:29,34–41` есть `Semaphore`, `tryAcquire()` и `finally { release() }`. Наличие 503 подтверждается `Application.kt:44–45`. Остаются **размер/срок хранения**, а не отсутствие лимита параллельности.
2. **Старый пункт 3 (несовпадающий порядок одинаково начинающихся реплик): исправлен.** Схема содержит `SubtitleLine.ordinal` (`AppDatabase.sq:20`), обе выборки используют `ORDER BY ... startMs, ordinal, id` (`:56,67`), `saveContent()` записывает ordinal по позиции списка (`SqlDelightContentRepository.kt:67–69`), миграция `1.sqm` добавляет поле. Отдельная проверка SQLite ниже подтверждает семантику миграции/ссылок. Порядок для *старых* одинаковых начал восстановить невозможно: ID применяется как согласованная детерминированная замена.
3. **Старый пункт 2 (аудио без ссылки): остаётся** — LK-02.
4. **Старый пункт 4 (вкладки): остаётся** — LK-04.

Положительно: backend URL ограничен HTTPS и допустимыми YouTube host/path (`YouTubeIngestionService.kt:94–108`), запуск yt-dlp идёт через отдельные аргументы, без shell (`YtDlpRunner.kt:28–33`), ошибки SRT не возвращают частичный список, схема использует FK и транзакции, Web-драйвер пытается завершать транзакцию в `NonCancellable` и сериализует worker-сообщения. Это оценка реализации, а не гарантия отсутствия крайних случаев при выполнении.

## 4. Известные ограничения, не приравненные к ошибкам

- Перевод через `MockLinguisticAssistant`, полноценное SRS-обучение, PWA, авторизация и полноценная canvas-доступность — планируемые функции, а не поломки заявленного MVP.
- Android по умолчанию отключён и требует отдельной проверки сборки/устройства; его ошибки не включены в основной Web-вердикт.
- Origin браузера и production reverse proxy должны быть настроены согласованно; `PUBLIC_BASE_URL` должен совпадать с публичным Web-origin. При неправильном origin CORS/mixed-content и разделение IndexedDB ожидаемы — это в первую очередь вопрос конфигурации.
- В `YtDlpRunner` существует десятиминутный таймаут и принудительная остановка процессов при ошибке/отмене; независимая проверка реального дерева процессов на Windows/Linux не проведена.
- Веб-хранилище не является резервной копией; удаление данных origin браузером уничтожает локальные SQLite и audio. LK-05 описывает *частичную* потерю аудио при сохранённом контенте.

## 5. Вопросы и гипотезы для дальнейшего исследования

1. **Одновременные записи из разных вкладок:** `DatabaseAccess` сериализует один connection, не несколько workers. Проверить VFS-locking, конфликт транзакций, послеаварийное восстановление и повтор открытия. Не утверждается, что данные сейчас повреждаются.
2. **Отложенное воспроизведение после IndexedDB:** в `AudioPlayerImpl.kt:74–86,96–111` `play()` может фактически вызываться после долгого await, уже без активного пользовательского жеста. Проверить блокировку autoplay в Chromium при медленном чтении большого Blob; без runtime-проверки это гипотеза, не находка.
3. **Удаление временных логов процесса при отмене в момент создания:** `YtDlpRunner.kt:23–27` создаёт log перед `try/finally`; проверить границу отмены между возвращением `withContext` и входом в `try`, а также Windows-ошибки `delete()`. Нужен управляемый concurrency test; сейчас не объявляется подтверждённой утечкой.
4. **Проверка нештатного `Content-Length`/HTTP Range/потоковой загрузки:** без настоящего сервера и браузера контракт успеха чтения проверен не полностью.

## 7. Предлагаемый порядок исправления

1. Перед публичным доступом: **LK-01** — бюджет импорта, квота и уборка backend.
2. Для предотвращения накопления мусорных данных: **LK-02 + LK-03** — компенсация завершённого аудио и восстановление незавершённых записей при старте.
3. Для достоверного Web UI и многовкладочности: **LK-04**, после параллельного browser-теста.
4. Для устойчивости плеера: **LK-05** с fallback и тестом отсутствующего audio manifest.
5. Для диагностики неправильного reverse proxy: **LK-06** и fixture некорректного media response.

Не требуется переписывать архитектуру целиком. Перечисленные проблемы локальны по границам транзакций, протоколу storage и жизненному циклу Web-приложения.

## 8. Что нельзя подтвердить по этому архиву

- Полную Kotlin/Gradle компиляцию, production bundle, реальную интеграцию Ktor/yt-dlp/FFmpeg/YouTube, HTTP Range и cancellation-disconnect под нагрузкой: нет скачанного Gradle и внешних зависимостей.
- Прохождение 67/24 тестов, их качество и покрытие: тесты сознательно исключены.
- Настоящие браузерные сценарии IndexedDB/WASM, multi-tab, quota/eviction, сбой tab/worker, autoplay, корректность blob-url lifecycle в разных браузерах.
- Поведение Android/ExoPlayer на устройстве и Android opt-in сборку.
- Успешный hosted CI run после исправлений, свежие CVE/уязвимости библиотек, настройки продакшн-окружения и права доступа внешнего сервера.
- Гарантированную очистку процессов и всех временных файлов на каждой ОС при принудительном завершении/потере питания.

**Итог:** замечания из старого отчёта нужно оценивать по текущему коду: лимит параллельности и порядок реплик исправлены, но остаются известные проблемы жизненного цикла аудио и межвкладочного состояния. К ним добавляются сценарии после внезапного закрытия вкладки и при частичной утрате локального аудио. Все runtime-сценарии необходимо подтвердить тестами перед слиянием исправлений.
