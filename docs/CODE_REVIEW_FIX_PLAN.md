## LK-02: аудио опубликовано, но не привязано к SQLite

**Где менять:** `IngestContentUseCase`, `ContentRepository`/`SqlDelightContentRepository`, `AudioStorage` и обе реализации storage, SQLDelight-запросы.

Минимальный вариант для обычных ошибок:

1. Добавить идемпотентное `AudioStorage.delete(location)`. Web удаляет manifest и чанки одной транзакцией. JVM принимает только собственные файлы из каталога storage, проверяя разрешённый абсолютный путь; произвольный путь удалять нельзя.
2. Выполнять привязку аудио узким запросом `UPDATE Content SET localAudioPath = ... WHERE id = ...`, а не повторно сохранять весь устаревший снимок контента/субтитров.
3. После публикации выполнять короткую операцию привязки и, при подтверждённом неуспехе, компенсационную очистку. Сетевую загрузку оставить отменяемой. Очистка при отмене выполняется в `NonCancellable`, исключение отмены пробрасывается.
4. Сохранить удалённые метаданные и прежнее аудио, если новое скачивание/привязка не удались. Ошибка очистки не должна скрывать исходную ошибку; её нужно сохранить как suppressed/диагностику.

**Критический нюанс:** исключение отмены при возврате из сменившего dispatcher `withContext` не доказывает rollback SQLite. COMMIT мог уже пройти. Безусловное удаление аудио в `catch` может создать обратный дефект: ссылка в БД есть, а файла нет. Проверку исхода и компенсацию нужно согласовать внутри repository с тем же `DatabaseAccess`, с учётом конкурирующих операций. Если исход commit нельзя достоверно установить, аудио сохранить как pending для последующей сверки, а не удалять вслепую. Также проверить передачу владения location при возврате из `FileAudioStorage.store`, который сам использует `withContext`.

Для полного восстановления после аварийного закрытия нужен долговечный учёт pending-объектов и сверка с SQLite. Одного `delete` в `catch` достаточно только для обработанных ошибок; это не закрывает аварийное завершение между публикацией и привязкой.

**Проверки:** сбой именно финальной записи; отмена до привязки; отмена после реального COMMIT; сбой самой очистки; повторное выполнение delete; отсутствие удаления старого/чужого/уже привязанного аудио. Использовать существующие `IngestContentUseCaseTest`, `IngestionRepositoryTest`, `FileAudioStorageTest`, `WebStorageTest`.

## LK-03: незавершённые загрузки переживают закрытие страницы

**Где менять:** `shared/src/jsMain/storage/index.js`, Kotlin bindings, инициализация Web storage; регрессионный сценарий — в `browser.test.js`.

Добавить manifest-поля `ownerId`, `updatedAt` и lease загрузки. Каждая запись чанка обновляет время; активный владелец продлевает lease при длительном ожидании сети. При старте и периодически удалять просроченные незавершённые manifest и их чанки одной IndexedDB-транзакцией. Повторное удаление безопасно. Если lease уже отобран уборкой, старый writer должен завершиться ошибкой, а не продолжать создавать чанки.

**Защита вкладок:** TTL сам по себе не доказывает отсутствие активного writer — вкладки замораживаются, таймеры throttled, ноутбук уходит в сон. Нельзя удалять все `complete: false` при каждом открытии БД. Для более строгой защиты можно удерживать отдельный Web Lock на время загрузки, а уборке брать такой же lock без ожидания; поддержку браузера нужно проверить, TTL оставить для аварийных/старых записей. Старые manifest без новых полей требуют консервативной политики миграции, а не немедленного удаления.

Pending-сверку завершённых непривязанных объектов из LK-02 лучше выполнять тем же механизмом восстановления, но по отдельному правилу: завершённый объект нельзя удалять только по возрасту без проверки ссылок SQLite и активного владельца.

**Проверки:** закрытие страницы без abort; уборка после заданного времени с внедряемыми часами; сохранность complete-объекта; сохранность загрузки второй вкладки; writer после истёкшего lease; повторная уборка; устаревший формат manifest. Крупные значения TTL не нужно реально выжидать в тестах.

## LK-04: другая вкладка не обновляет библиотеку

**Где менять:** `BrowserSqlDriver`, Web bindings/worker client либо отдельный Web-механизм уведомлений; `DatabaseAccess` и фабрика соединения — для безопасного перечитывания.

После успешного внешнего commit публиковать в `BroadcastChannel` сигнал об изменённых таблицах с идентификатором отправителя. Для одиночных запросов вне транзакции — после успешного выполнения. Сигналы незавершённой/откаченной транзакции не публиковать. Получатель вызывает только локальную инвалидацию SQLDelight-запросов и не рассылает сигнал обратно. Закрывать канал вместе с driver; при возврате вкладки в фокус дополнительно перечитывать библиотеку, поскольку сообщения можно пропустить.

**Критический нюанс:** callbacks не должны выполнять SQL в обход общего `DatabaseAccess`, особенно во время чужой локальной транзакции. Нынешние repository Flow перечитывают через `access.run`; сохранить это правило. `BroadcastChannel` решает уведомления, но не блокировки SQLite/VFS: успешность одновременных записей из разных worker нужно проверить отдельно. Если обнаружится ограничение VFS, это отдельное исправление координации записи, а не основание объявлять потерю данных заранее.

**Проверки:** две страницы одного browser context; A импортирует, Flow в B обновляется без reload; rollback в A не публикует данные; нет эхо-цикла; закрытый driver не получает событий; параллельные записи разных объектов сохраняются после reopening.

## LK-05: отсутствующее локальное аудио блокирует сетевое воспроизведение

**Где менять:** `AudioPlayer`, Web/Android реализации, `PlayerViewModel`, состояние/события UI и при необходимости узкий запрос обновления локальной ссылки.

Вместо одного текста ошибки ввести структурированную причину и идентификатор текущей загрузки: локальный объект отсутствует/неполон, временная ошибка storage, сетевой сбой, запрет autoplay. При подтверждённом отсутствии локального объекта предложить «Воспроизвести по сети» или один раз загрузить `content.audioUrl` с явным сетевым состоянием. Для MVP ручное действие проще контролировать: оно сохраняет пользовательский жест браузера и не запускает неожиданную сетевую загрузку.

Общий `error: String?` недостаточен для надёжного fallback: перевод текста ошибки не должен менять поведение. Устаревшая ошибка предыдущего контента не должна переключать новый контент. Запрет autoplay и временная недоступность IndexedDB не являются доказательством отсутствия аудио. Если очищать устаревшую ссылку в SQLite, делать это условно для прежнего location; не стирать ссылку на уже скачанный в другой операции новый файл.

**Проверки:** удалить только аудио, сохранив SQLite; успешный remote fallback; недоступный remote показывает понятную ошибку без цикла; запрет autoplay не очищает ссылку; ошибка старой загрузки не влияет на новую; корректный локальный файл не вызывает HTTP-запросов.

## LK-06: HTML/JSON с HTTP 200 сохраняется как аудио

**Где менять:** `ContentApi.download`, маршрут media в backend, `ContentApiTest` и интеграционные HTTP fixtures.

Быстрое исправление: до передачи данных storage отклонять явно неподходящий `Content-Type` — HTML, JSON и текстовые ошибки. Backend должен явно отдавать согласованный тип Opus-контейнера. Пустой ответ и неполный `Content-Length` уже проверяются storage, сохранить эти проверки.

Более строгий вариант: проверить начало потока до публикации. Для backend-контракта Ogg/Opus проверить сигнатуру `OggS` и, если нужно подтвердить именно Opus, заголовок `OpusHead`; одна сигнатура Ogg не доказывает аудиокодек. Прочитанный префикс нужно вернуть в поток storage, не теряя байты и не буферизуя весь файл. Нельзя безусловно требовать только `audio/opus`: сервер может использовать `audio/ogg` или `application/ogg`. Политику для отсутствующего MIME/`application/octet-stream` определить явно, опираясь на сигнатуру.

Существующие unit-fixtures иногда используют строку `opus`, а browser-fixtures — настоящий WAV. При строгой проверке изменить unit-fixtures на валидный контейнер и явно решить, допускает ли контракт WAV для тестового сервера. Не менять production-контракт незаметно ради старых тестов.

**Проверки:** HTML/JSON с 200 и корректной длиной не доходит до `store`; валидный Opus принимается; неверная сигнатура отклоняется; короткое тело и поток без Content-Length; префикс не теряется; отмена и неполный ответ очищают частичные данные.

## LK-01: бюджеты backend и политика хранения

**Где менять:** сервис импорта, runner, конфигурация backend и выдача media. Существующий semaphore сохранить.

1. Создавать отдельный каталог для каждого импорта, чтобы учитывать исходный media-файл, `.part`, конвертируемое аудио, субтитры и метаданные вместе. Учитывать также временные логи процесса, которые сейчас создаются вне downloads.
2. До большого скачивания отклонять видео с недопустимой длительностью/оценкой размера; неизвестную длительность и live-потоки обрабатывать по явно заданной политике. После завершения повторно проверить фактические метаданные/объём.
3. В процессе загрузки контролировать фактические байты и останавливать дерево процессов при превышении. Флаги yt-dlp по оценочному размеру не заменяют фактическую квоту, особенно при конвертации. Периодический монитор тоже допускает превышение между опросами; для строгой границы нужна квота/изоляция на уровне ОС или файловой системы.
4. Ввести общий бюджет с резервированием под параллельные импорты. Проверка «есть место» без резерва допускает, что два запроса займут одно и то же свободное место. Внешние процессы также могут занять диск, поэтому отказ записи остаётся штатной ошибкой с cleanup.
5. После импорта удалять ненужные промежуточные файлы. TTL/eviction должен исключать активные загрузки и media, которое сейчас отдаётся клиенту. Объяснить пользователю срок жизни сетевого аудио: удаление серверного файла сломает remote-only контент. На Windows удаление открытого файла может не выполниться — результат удаления нужно проверять.
6. Настроить размер, длительность, общий бюджет и retention через конфигурацию; значения лимитов выбрать под целевое окружение. Публичный доступ дополнительно ограничить авторизацией/rate limit либо оставить только доверенный вход.

**Проверки:** чрезмерная длительность до скачивания; превышение фактических байтов с остановкой и cleanup; два конкурентных запроса при недостаточном бюджете; освобождение резерва при ошибке/отмене; TTL не удаляет активный импорт/поток; после TTL неизвестный media возвращает 404; ошибка удаления видна в диагностике.

## Порядок выполнения

- Основной пакет надёжности: **LK-02 + LK-03**, поскольку компенсация и аварийное восстановление относятся к одному жизненному циклу аудио. Разбить на отдельные проверяемые изменения: контракт удаления/привязки, затем leases/recovery.
- Независимые небольшие изменения: **LK-06** (сначала явные HTML/JSON-ответы), затем **LK-05** (типизированная ошибка и ручное воспроизведение по сети).
- Затем **LK-04**, начиная с браузерного воспроизведения в двух вкладках и проверки VFS.
- **LK-01 обязателен до публичного размещения**, даже если продуктовые исправления выше ещё в работе. Не считать его закрытым после добавления одних флагов yt-dlp.

Для каждого изменения сначала добавить воспроизводящий регрессионный тест в полном репозитории, затем исправлять код и запускать релевантные JVM/Web-проверки. Спорные гипотезы из входящего отчёта (autoplay после await, VFS-конкурентность, создание временного лога на границе отмены) пока не переводить в подтверждённые баги.
