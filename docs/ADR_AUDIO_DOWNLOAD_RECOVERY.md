# ADR: восстановление download по content lease

Статус: принято, REL-S2/REL-02–REL-09, 2026-10-22.

## Проблема

После закрытия вкладки статус Content остаётся DOWNLOADING и отключает повторную загрузку. Asset lock защищает только запись чанков: до beginAudio и после commitAudio downloader ещё работает с HTTP/SQLite. Уборка статуса по одному asset lock может прервать активную операцию.

## Рассмотренные варианты

- Сбросить все DOWNLOADING при запуске: просто, но повреждает состояние загрузок другой вкладки.
- TTL/heartbeat: допускает ложное истечение при заморозке вкладки/сне, поэтому не доказывает завершение владельца.
- Отдельный Web Lock на content в течение всей операции плюс долговечная метка известного протокола: защищает активного владельца и отличает новые операции от старых вкладок, не использующих блокировку. Выбран этот вариант.

## Контракт

AudioDownloaderImpl получает lease перед чтением/изменением SQL и освобождает после привязки/компенсации в NonCancellable. Изменение DOWNLOADING и метки `audio_download_lock:<id>` со значением `web-lock-v1` выполняется одной транзакцией. Успех/обработанная ошибка транзакционно удаляют метку вместе со сменой статуса.

При запуске WebDatabaseFactory вызывает AudioDownloadRecovery. Для каждого DOWNLOADING recovery берёт тот же content lock без ожидания и под DatabaseAccess в транзакции перечитывает Content и метку. Только известный протокол при свободном lock допускает восстановление: ERROR без прежнего localAudioPath; COMPLETED с сохранением прежнего пути. Существование файла здесь не проверяется: сохранённая ссылка остаётся прежней, а отдельная проверка воспроизведения обрабатывает недоступное аудио.

## Ограничения

В Web без Web Locks и для старых/неизвестных меток автоматического сброса нет. Живая вкладка сохраняет своё состояние, в том числе при длительном ожидании сети. Новые вкладки не получают автоматические уведомления о внешней recovery: полноценная инвалидация Flow остаётся LK-04. Схема SQLite не изменяется: метка использует существующую SyncMetadata.

## REL-04: Desktop/TUI

Одного Mutex недостаточно: Desktop и TUI могут быть разными процессами с одним профилем. PID/таймаут также не доказывает конец загрузки. Выбран отдельный FileChannel.tryLock на каждый content; FileAudioDownloadCoordinator реализует тот же AudioDownloadCoordinator с протоколом `jvm-file-lock-v1`. DesktopModule регистрирует его для downloader и createJvmDatabase. При повторном открытии БД AudioDownloadRecovery применяет ту же проверку lease/метки и восстановление ERROR/COMPLETED.

Каталог — `<LANGKRAFT_DATA_DIR>/download-locks`; имя lock-файла — SHA-256 contentId, так что ID не становится путём. Реестр JVM запрещает второй канал для того же canonical path до освобождения. Native FileLock и канал удерживаются токеном. Идемпотентный release закрывает ресурсы в NonCancellable; отмена при возврате из IO также закрывает уже полученный lease.

Файловые lock используются как кооперативные: все участвующие writers должны соблюдать протокол. Закрытие другого канала к тому же файлу на некоторых системах может освободить lock JVM, поэтому реестр не допускает такого открытия. Удалять/переименовывать lock-файлы при работающих процессах нельзя: владение определяется lock, а не существованием файла. Эти свойства и ограничения network filesystems описаны в [Java FileLock](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/channels/FileLock.html). Реализация не подменяет ошибку файловой системы неблокируемым режимом; ошибка возвращается.

Проверены локальная файловая система и отдельные JVM: конкурентный процесс получает BUSY, а после принудительного завершения владельца БД восстанавливается. Это не проверка всех одновременных SRS/sync/migration сценариев и не сертификация сетевого профиля. Файловый pending-журнал добавлен в REL-05; legacy/неизвестные SQL-метки сохраняются.

## REL-05: файловый pending-журнал

JournaledFileAudioStorage декорирует FileAudioStorage и реализует PendingAudioStorage. До открытия `.part` callback beforeWrite записывает `<asset>.mp3.pending`: JSON с version=1, contentId и fileName. Запись создаётся как новый обычный файл и завершается force(true) под native content lease. Только после этого начинается запись payload. Поэтому после завершения процесса journal описывает и незавершённый `.part`, и готовый MP3 до SQL link.

После SQL COMMIT confirmLinked проверяет final-файл и удаляет sidecar, пока lease ещё удерживается. Если подтверждение не удалось, SQL link и данные не откатываются. При старте общая PendingAudioRecovery берёт свободный lease, проверяет все ссылки SQLite под DatabaseAccess и вызывает resolvePending: при ссылке сохранить MP3 и подтвердить; без ссылок удалить final/partial, затем журнал. Ссылка на отсутствующий final сохраняет journal/partial и не допускает удаления по догадке.

Файловая система не предоставляет транзакцию удаления трёх независимых файлов. Поэтому журнал удаляется последним, а неполная уборка повторяется после следующего запуска. При ошибке удаления результат виден вызывающему коду, sidecar сохраняется. Обработанная ошибка store удаляет sidecar только когда final и `.part` уже отсутствуют. Отмена на границе dispatcher входит в тот же механизм компенсации.

Кандидаты ограничены известной версией journal, проверенным contentId/UUID-именем в managed audio-каталоге и обычными файлами без следования symlink. Некорректные, слишком большие, неизвестные и legacy sidecar сохраняются; файлы без sidecar никогда не подбираются этой уборкой. Исчезновение sidecar между чтениями считается уже выполненной сверкой. Все новые SQL-ссылки на pending asset обязаны вводиться под lease исходного contentId.

DesktopModule передаёт один экземпляр FileAudioDownloadCoordinator и JournaledFileAudioStorage в downloader и startup recovery. Android сохраняет обычный FileAudioStorage: его target не включён. Подтверждённое аудио после удаления Content относится к отдельной retention. Гарантия этого этапа проверена для аварийного завершения процесса; потеря питания/оборудования и durable directory metadata отдельно не подтверждены.

## REL-03: опубликованные pending-объекты

Удалять все готовые объекты без текущей ссылки небезопасно: владелец может ещё выполнять SQL link. Уборка только по возрасту также не доказывает окончания операции. Поэтому beginAudio помечает объект `pendingVersion=1, pending=true` только когда этот же JS-модуль уже удерживает полный content lease. commitAudio сохраняет метку при публикации. Старые/no-lock загрузки исключены из протокола.

После COMMIT SQL link downloader вызывает AudioStorage.confirmLinked под всё ещё удерживаемым lease. Web-адаптер атомарно снимает pending. При отказе подтверждения ошибка возвращается, но готовое аудио и SQL link не откатываются; следующая сверка подтвердит ссылку заново.

PendingAudioRecovery вызывается при старте после incomplete/SQL recovery. Для каждого кандидата берётся свободный lease его исходного contentId. Под общим DatabaseAccess проверяются ссылки **всех** Content, затем IndexedDB повторно проверяет complete/pending/версию и владение content lease. Ссылка есть — снять pending; ссылки нет — одной IDB-транзакцией удалить manifest/chunks. Неуспешное/неизвестное SQL-чтение запрещает удаление. SQLite-транзакция не удерживается во время IDB; согласование штатного publisher и уборщика обеспечивает общий content lease.

Все новые ссылки на ещё pending-объект должны создаваться под lease его исходного contentId. Штатный downloader соблюдает это правило. Ручные SQL-изменения и будущие пути импорта должны соблюдать тот же контракт; DatabaseAccess сам по себе защищает только один локальный worker.

| Момент аварии | Следующий запуск |
| --- | --- |
| До commitAudio | Уборка incomplete manifest/chunks при свободном asset lock |
| После публикации, до SQL link | Pending сверка удаляет объект при свободном content lease и отсутствии всех SQL-ссылок |
| После SQL link, до confirmLinked | Pending сверка сохраняет объект и снимает метку |
| После confirmLinked | Объект больше не кандидат pending GC, даже после удаления Content |

Это восстановление незавершённой передачи владения, а не общая retention/квота. Подтверждённые и legacy/no-lock объекты автоматически не удаляются. Версии IndexedDB и SQLite не меняются, поля manifest добавляются совместимо.

## REL-06: legacy/no-lock

У старой версии нет доказуемого lease. Автоматический reset/TTL-сборка могли бы вмешаться в живой процесс. Выбран консервативный вариант: исходник сохраняется, восстановление Desktop/TUI выполняется в отдельную копию через SQLite backup API. Сброс статусов допустим в копии, поскольку старый writer не работает с её путями/БД. Доступное связанное audio копируется с проверкой неизменности и переназначением путей; partial/неизвестные/внешние объекты не переносятся.

Утилита удаляет токен только в копии, сохраняя pending sync/SRS и исходную сессию. Существующий профиль не перезаписывается; незавершённый результат остаётся `.preparing-*`, а готовое назначение публикуется после проверки. SQLite snapshot согласован, но вся файловая система не заморожена: недоступное/изменившееся audio отражается в отчёте и ERROR копии. Web export/copy остаётся отдельным backlog; IndexedDB не очищается. [Политика и команды](LEGACY_RECOVERY.md).

## REL-07: Web legacy export/copy

REL-07 реализует Web export/copy на отдельной recovery.html. Выбран readonly-снимок исходных IndexedDB и создание нового UUID-профиля вместо reset исходника или переключения активной БД приложения. Альтернатива — открывать источник через SQLite и VACUUM — привязала бы recovery к writable VFS/startup и блокировкам исходника; raw IDB export без компактирования мог бы вынести историю удалённых токенов. Поэтому raw VFS читается readonly, SQL исправляется в отдельной копии, а архив формируется VACUUM INTO MemoryVFS только после удаления auth. При импорте компактные SQLite pages снова размещаются в отдельном IDBBatchAtomicVFS и проходят валидацию.

SQL-файлы и download locks имеют пространство имён профиля; исторические default names сохранены. SQLite-файл копии сокращён до UUID без дефисов: bundled wa-sqlite 1.0 ограничивает VFS path 64 байтами вместе с journal suffix. Снимки SQL и audio не атомарны между собой, поэтому недоступные ссылки сбрасываются только в копии. Новые зависимости/SQL-миграции не вводились. MemoryVFS — существующий инфраструктурный Adapter из wa-sqlite, recovery остаётся JS-модулем с функциями, без искусственной GoF-иерархии. Лимиты и пользовательский сценарий — [LEGACY_RECOVERY](LEGACY_RECOVERY.md).

## REL-09: ручное удаление recovery-v2

Новый идентификатор `recovered-v2-<UUID>` отделяет управляемые копии от старых сборок: прежний validator их отвергает. Основной профиль и старые recovery-ID остаются совместимыми, но удаление для них запрещено. `profile-lifecycle.js` хранит реестр состояний в отдельной IndexedDB `langkraft-recovery-profiles-v2`, store `profiles`, version 1. Версии SQLite VFS/audio/client schema не меняются.

Shared Web Lock `langkraft-profile-lifetime:<ID>` удерживается SQL-воркером до graceful close/terminate, audio-модулем до уничтожения страницы и recovery-операцией на всё время чтения/записи. Открытие v2 требует active в реестре. Создание регистрирует новый ID через add под shared lease; повторное использование ID запрещено. Эксклюзивный ifAvailable lock удаления даёт немедленный отказ при активном владельце и запрещает новые открытия. Вкладки с кэшированным аудио тоже считаются владельцами.

Перед очисткой реестр strict-транзакцией переводит профиль в deleting. Затем отдельными strict-транзакциями очищаются известные stores существующих БД; отсутствующая БД не создаётся. После обеих очисток ставится deleted. Это повторяемая операция, без общей транзакции двух БД. Отказ сохраняет deleting, запрещает запуск половины профиля и позволяет повторить очистку. Постоянный tombstone предотвращает воссоздание данных по старой ссылке. Inventory читает имена БД и реестр, скрывает deleted и предлагает повтор для deleting.

Альтернатива deleteDatabase отклонена: blocked-запрос не отменяется и может выполниться позже. Вместо него очищаются записи: остаются пустые DB-контейнеры и небольшой реестр. Полное освобождение browser quota не гарантируется. Ручная очистка реестра, вмешательство DevTools или другого same-origin кода вне протокола не поддерживаются. Нет TTL, автоматического удаления оригиналов и общей retention медиа.

Проверки: SQL/audio/source recovery исключают удаление; закрытие страницы/worker снимает lock; удалённые ссылки и частичный результат не открываются; повтор после сбоя между БД завершает очистку. Оригинал и его auth/SRS сохраняются. UI проверяет отмену подтверждения, отказ при открытом приложении и успех после закрытия. Проверяется отсутствие вызовов deleteDatabase.

## Проверка REL-07

Recovery Chromium-тест проверяет активные SQL/audio writers, общий asset, SRS/cues/queue, повреждённые/внешние/partial ссылки, удаление token history из экспорта, round-trip архива, отказ будущей схемы, существующего назначения и отсутствующего источника. UI-регресс создаёт/экспортирует/импортирует копию реальной библиотеки и открывает её полным Compose-клиентом.

## Проверка протоколов REL-02–REL-05

AudioDownloadRecoveryTest и AudioDownloaderTest проверяют ошибки, отмену, rollback и освобождение lease. Web UI-тест удерживает HTTP-ответ, проверяет SQL-метку и недоступность lease, затем моделирует перезапуск, активного/закрытого владельца второй вкладки и legacy-запись.

PendingAudioRecoveryTest проверяет ссылку другого Content, отсутствие Content, ошибку SQL/IDB, отмену, недоступный/неизвестный протокол и повторную сверку. Storage-тест проверяет запрет resolve без lease и атомарное удаление manifest/chunks; UI-тест — неприкреплённую публикацию, публикацию активного владельца, связь другого Content, подтверждение и сохранность legacy/offline аудио.

FileAudioDownloadCoordinatorTest проверяет native lease, реестр, пространства каталогов/content, повтор после ошибки и отмену при возврате. JvmDownloadRecoveryTest открывает настоящую SQLite до/после сбоя, сохраняет старое audio и legacy, запускает отдельную JVM-владельца и проверяет download через HTTP mock + FileAudioStorage. NativeFileLockProbe — тестовая source-launch Java программа, запускаемая установленным JDK.

JournaledFileAudioStorageTest проверяет порядок journal/partial, успешное подтверждение, обработанную ошибку, отмену при возврате, запрет resolve без lease, неизвестный формат и повтор после частичного отказа удаления. JvmDownloadRecoveryTest проверяет crash после публикации, ссылку другого Content и исключение подтверждённых файлов из retention. NativeFileLockProbe записывает и force-сохраняет partial под живым lock; после принудительного завершения startup восстанавливает SQL и удаляет journal/partial.
