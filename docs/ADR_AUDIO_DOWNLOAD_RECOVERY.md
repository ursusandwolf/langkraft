# ADR: восстановление download по content lease

Статус: принято, REL-S2/REL-02–REL-04, 2026-10-22.

## Проблема

После закрытия вкладки статус Content остаётся DOWNLOADING и отключает повторную загрузку. Asset lock защищает только запись чанков: до beginAudio и после commitAudio downloader ещё работает с HTTP/SQLite. Уборка статуса по одному asset lock может прервать активную операцию.

## Рассмотренные варианты

- Сбросить все DOWNLOADING при запуске: просто, но повреждает состояние загрузок другой вкладки.
- TTL/heartbeat: допускает ложное истечение при заморозке вкладки/сне, поэтому не доказывает завершение владельца.
- Отдельный Web Lock на content в течение всей операции плюс долговечная метка известного протокола: защищает активного владельца и отличает новые операции от старых вкладок, не использующих блокировку. Выбран этот вариант.

## Контракт

AudioDownloaderImpl получает lease перед чтением/изменением SQL и освобождает после привязки/компенсации в NonCancellable. Изменение DOWNLOADING и метки `audio_download_lock:<id>` со значением `web-lock-v1` выполняется одной транзакцией. Успех/обработанная ошибка транзакционно удаляют метку вместе со сменой статуса.

При запуске WebDatabaseFactory вызывает AudioDownloadRecovery. Для каждого DOWNLOADING recovery берёт тот же content lock без ожидания и под DatabaseAccess в транзакции перечитывает Content и метку. Только известный протокол при свободном lock допускает восстановление: ERROR без прежнего localAudioPath; COMPLETED с сохранением прежнего пути. Существование файла здесь не проверяется: сохранённая ссылка остаётся прежней, а отдельная проверка воспроизведения обрабатывает недоступное аудио.

## Ограничения

В Web без Web Locks и для старых/неизвестных меток автоматического сброса нет. Живая вкладка сохраняет своё состояние, в том числе при длительном ожидании сети. Новые вкладки не получают автоматические уведомления о внешней recovery: полноценная инвалидация Flow остаётся LK-04. Схема SQLite не изменяется: метка использует существующую SyncMetadata.

## REL-04: Desktop/TUI

Одного Mutex недостаточно: Desktop и TUI могут быть разными процессами с одним профилем. PID/таймаут также не доказывает конец загрузки. Выбран отдельный FileChannel.tryLock на каждый content; FileAudioDownloadCoordinator реализует тот же AudioDownloadCoordinator с протоколом `jvm-file-lock-v1`. DesktopModule регистрирует его для downloader и createJvmDatabase. При повторном открытии БД AudioDownloadRecovery применяет ту же проверку lease/метки и восстановление ERROR/COMPLETED.

Каталог — `<LANGKRAFT_DATA_DIR>/download-locks`; имя lock-файла — SHA-256 contentId, так что ID не становится путём. Реестр JVM запрещает второй канал для того же canonical path до освобождения. Native FileLock и канал удерживаются токеном. Идемпотентный release закрывает ресурсы в NonCancellable; отмена при возврате из IO также закрывает уже полученный lease.

Файловые lock используются как кооперативные: все участвующие writers должны соблюдать протокол. Закрытие другого канала к тому же файлу на некоторых системах может освободить lock JVM, поэтому реестр не допускает такого открытия. Удалять/переименовывать lock-файлы при работающих процессах нельзя: владение определяется lock, а не существованием файла. Эти свойства и ограничения network filesystems описаны в [Java FileLock](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/channels/FileLock.html). Реализация не подменяет ошибку файловой системы неблокируемым режимом; ошибка возвращается.

Проверены локальная файловая система и отдельные JVM: конкурентный процесс получает BUSY, а после принудительного завершения владельца БД восстанавливается. Это не проверка всех одновременных SRS/sync/migration сценариев и не сертификация сетевого профиля. Файлового pending-журнала пока нет: `.part` и готовые непривязанные файлы автоматически не удаляются. Legacy/неизвестные SQL-метки также сохраняются.

## REL-03: опубликованные pending-объекты

Удалять все готовые объекты без текущей ссылки небезопасно: владелец может ещё выполнять SQL link. Уборка только по возрасту также не доказывает окончания операции. Поэтому beginAudio помечает объект `pendingVersion=1, pending=true` только когда этот же JS-модуль уже удерживает полный content lease. commitAudio сохраняет метку при публикации. Старые/no-lock загрузки исключены из протокола.

После COMMIT SQL link downloader вызывает AudioStorage.confirmLinked под всё ещё удерживаемым lease. Web-адаптер атомарно снимает pending. При отказе подтверждения ошибка возвращается, но готовое аудио и SQL link не откатываются; следующая сверка подтвердит ссылку заново.

PendingAudioRecovery вызывается при старте после incomplete/SQL recovery. Для каждого кандидата берётся свободный lease его исходного contentId. Под общим DatabaseAccess проверяются ссылки **всех** Content, затем IndexedDB повторно проверяет complete/pending/версию и владение content lease. Ссылка есть — снять pending; ссылки нет — одной IDB-транзакцией удалить manifest/chunks. Неуспешное/неизвестное SQL-чтение запрещает удаление. SQLite-транзакция не удерживается во время IDB; согласование штатного publisher и уборщика обеспечивает общий content lease.

Все новые ссылки на ещё pending-объект должны создаваться под lease его исходного contentId. Штатный downloader соблюдает это правило. Ручные SQL-изменения и будущие пути импорта должны соблюдать тот же контракт; DatabaseAccess сам по себе защищает только один локальный worker.

| Момент аварии | Следующий запуск |
| --- | --- |
| До commitAudio | Уборка incomplete manifest/chunks при свободном asset lock |
| После публикации, до SQL link | Pending сверка удаляет объект при свободном content lease и отсутствии всех SQL-ссылок |
| После SQL link, до confirmLinked | Pending сверка сохраняет объект и снимает метку |
| После confirmLinked | Объект больше не кандидат pending GC, даже после удаления Content |

Это восстановление незавершённой передачи владения, а не общая retention/квота. Подтверждённые и legacy/no-lock объекты автоматически не удаляются. Версии IndexedDB и SQLite не меняются, поля manifest добавляются совместимо.

## Проверка

AudioDownloadRecoveryTest и AudioDownloaderTest проверяют ошибки, отмену, rollback и освобождение lease. Web UI-тест удерживает HTTP-ответ, проверяет SQL-метку и недоступность lease, затем моделирует перезапуск, активного/закрытого владельца второй вкладки и legacy-запись.

PendingAudioRecoveryTest проверяет ссылку другого Content, отсутствие Content, ошибку SQL/IDB, отмену, недоступный/неизвестный протокол и повторную сверку. Storage-тест проверяет запрет resolve без lease и атомарное удаление manifest/chunks; UI-тест — неприкреплённую публикацию, публикацию активного владельца, связь другого Content, подтверждение и сохранность legacy/offline аудио.

FileAudioDownloadCoordinatorTest проверяет native lease, реестр, пространства каталогов/content, повтор после ошибки и отмену при возврате. JvmDownloadRecoveryTest открывает настоящую SQLite до/после сбоя, сохраняет старое audio и legacy, запускает отдельную JVM-владельца и проверяет download через HTTP mock + FileAudioStorage. NativeFileLockProbe — тестовая source-launch Java программа, запускаемая установленным JDK.
