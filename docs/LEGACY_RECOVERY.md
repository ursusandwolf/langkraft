# Legacy/no-lock: аудит и восстановление в копию

Наличие старого DOWNLOADING, `.part` или manifest без протокола не доказывает завершения владельца. Старая вкладка/версия приложения может не использовать новый lock; TTL/PID не дают достаточной гарантии. Поэтому startup recovery сохраняет legacy/no-lock и неизвестные форматы. Автоматическое удаление старых объектов не включается.

Для Desktop/TUI доступна [утилита recovery](../tools/recovery/recover_legacy_profile.py): Python 3.10+, только стандартная библиотека. По умолчанию она выполняет read-only аудит. `--clone-to` создаёт отдельный восстановленный профиль, не изменяя SQL-данные и аудио исходного профиля. Это выход из зависшего состояния через изолированную копию, а не подтверждение отсутствия живого старого владельца.

## Аудит

Из корня проекта в PowerShell:

```powershell
$sourceProfile = Join-Path $env:USERPROFILE '.langkraft'
python tools/recovery/recover_legacy_profile.py --source $sourceProfile
```

Для настроенного LANGKRAFT_DATA_DIR передайте его фактический каталог. JSON содержит версию схемы, зависшие Content, метки протокола и инвентаризацию непосредственных записей `audio/`; состояние владельца остаётся unknown. Содержимое journal не интерпретируется, токен аккаунта не выводится. Ссылки/подкаталоги не обходятся рекурсивно. Отчёт — наблюдение, а не разрешение удалить перечисленные объекты.

## Изолированное восстановление Desktop/TUI

Назначение должно быть новым и не пересекаться с исходным профилем:

```powershell
$recoveredProfile = Join-Path $env:USERPROFILE '.langkraft-recovered'
python tools/recovery/recover_legacy_profile.py --source $sourceProfile --clone-to $recoveredProfile
$env:LANGKRAFT_DATA_DIR = $recoveredProfile
.\gradlew.bat :shared:run --args=--smoke
.\gradlew.bat :shared:run
```

Для TUI используйте `:shared:runTui`. В Bash:

```bash
python3 tools/recovery/recover_legacy_profile.py --source "$HOME/.langkraft" --clone-to "$HOME/.langkraft-recovered"
LANGKRAFT_DATA_DIR="$HOME/.langkraft-recovered" bash ./gradlew :shared:run --args=--smoke
```

Утилита делает следующее:

1. Открывает исходную SQLite с mode=ro/query_only и создаёт согласованный snapshot через SQLite backup API, включая committed WAL. Схема проверяется до и после снимка; версии новее v3 отклоняются.
2. Переносит только связанные готовые обычные файлы внутри исходного `audio/`. `.part`, sidecar, внешние и отсутствующие пути не копируются. Общий файл копируется один раз; отчёт содержит размер/SHA-256. Изменение размера, mtime или identity во время копирования отклоняет файл.
3. Переписывает localAudioPath на новый профиль. DOWNLOADING становится COMPLETED при успешно перенесённом старом аудио, иначе ERROR с пустым путём. Недоступное аудио других статусов также становится ERROR только в копии.
4. Сохраняет остальные таблицы: субтитры, словарь/SRS, теги, pending sync, source references и курсоры. Удаляет auth_token и старые audio_download_lock метки только в копии. Схема не мигрируется утилитой; старую поддерживаемую схему обновит приложение при первом запуске копии.
5. Проверяет SQLite quick_check, сохраняет recovery-report.json и публикует готовый каталог. Существующий профиль не перезаписывается. При ошибке назначения нет, временный `.preparing-*` каталог сохраняется с путём в ошибке; его нельзя считать завершённым профилем.

Исходный процесс может продолжать работу: SQL-снимок согласован, а меняющиеся/исчезнувшие audio отмечаются недоступными в копии. Дальнейшие изменения исходного профиля после снимка в копию не попадают. Это не атомарный снимок SQLite и всей файловой системы.

Сначала проверьте словарь, очередь повторений, библиотеку и offline-аудио в копии без входа в аккаунт. Затем выберите профиль для дальнейшей работы и авторизуйтесь в нём. Исходный профиль и его сессия остаются доступны; оригинал утилита не удаляет.

## Web legacy/no-lock

Python-утилита не работает с браузерным IndexedDB. Для старых/неизвестных manifest и окружений без Web Locks сохраняется политика без автоматического сброса/удаления. Восстановление нового протокола работает через [lease и pending](ADR_AUDIO_DOWNLOAD_RECOVERY.md); отсутствие Web Locks можно устранить запуском приложения в поддерживаемом secure context, но это само по себе не делает старые записи безопасными кандидатами GC.

В REL-07 добавлена отдельная страница `recovery.html` для восстановления Web в новый профиль. Очистка site data уничтожает библиотеку и не является способом безопасного восстановления. Общая retention подтверждённого/legacy-аудио остаётся отдельной задачей.

В разделе «Сохранённые копии» (REL-08) показаны recovery-профили этого origin и наличие двух хранилищ SQLite/audio. Можно открыть профиль или выбрать его источником восстановления. Список обновляется кнопкой и после каждой операции; частичные результаты тоже видны, но ссылок для них нет. Наличие двух БД не означает, что копия прошла проверку: список читает только имена через IndexedDB.databases(), не открывает и не меняет данные. Основной профиль не включён. Если браузер не поддерживает перечисление БД, появится сообщение; создание копий/экспорт/импорт остаются доступны.

Удаление пока не поддерживается. Для него требуется согласованная защита всех работающих клиентов профиля. Обычный deleteDatabase может остаться в состоянии blocked, а затем удалить БД после закрытия другой вкладки; такой запрос нельзя отменить. До внедрения протокола не используйте ручное удаление БД при открытых вкладках приложения. Время создания, размер и целостность из списка имён определить нельзя.

### Копия и архив в браузере

1. Откройте `http://127.0.0.1:3000/recovery.html` при локальном запуске или `recovery.html` на **том же origin**, где сохранена библиотека. Другой порт, hostname, браузер или browser profile не дают доступа к прежнему IndexedDB. Страница не запускает Compose, миграции или startup-очистку исходника.
2. Нажмите **Создать копию**. Утилита читает исходные SQLite VFS records и audio/chunks транзакциями readonly; source БД не открывается writable SQLite-драйвером. SQLite и audio снимаются отдельно: общего атомарного снимка двух IndexedDB нет. Доступное связанное audio проверяется по complete/count/size и последовательности чанков; отсутствующее, внешнее и неполное audio получает пустой путь/ERROR только в копии. Независимые SRS, cues, pending sync и курсоры сохраняются.
3. Откройте выданную ссылку вида `/?profile=recovered-<UUID>`. Для копии выделены отдельные IndexedDB, имя SQLite-файла и download locks. Вход в аккаунт и download-метки удаляются только из копии. Проверьте словарь, очередь повторений и offline audio, затем выберите профиль для дальнейшей работы. Сохраните ссылку: адрес без `profile` открывает основной профиль. Для восстановления уже созданной копии откройте `recovery.html?profile=<тот же ID>`.
4. **Экспортировать копию** создаёт ещё один изолированный профиль и скачивает `langkraft-recovery.json`. Архив содержит компактный SQLite через VACUUM INTO и связанные audio chunks в base64. Исторические VFS-записи/свободные страницы не экспортируются; удалённый токен не переносится в историю архива. Это формат восстановления Web v1, а не ZIP или desktop-профиль.
5. На странице восстановления выберите архив и нажмите **Восстановить из архива**. Создаётся новый UUID-профиль; импорт не подменяет основной или ранее созданный профиль. Можно импортировать архив на другом origin с этой версией приложения. После завершения проверяются SQLite quick_check и схема, затем публикуется ссылка.

Поддерживаются текущий wa-sqlite IndexedDB VFS v5, audio v1 и client SQL schema v1–v3. Неизвестные версии/структуры отклоняются. Нужен современный браузер с IndexedDB, WebAssembly и Web Locks в secure context (HTTPS или localhost). Данные от старого no-lock writer можно копировать в поддерживаемом браузере; среда без Web Locks не обходит требования SQLite VFS.

Архив ограничен 64 МиБ, каждый исходный бинарный набор (VFS или audio) — 64 МиБ, каждая object store — 50 000 записей. Снимки/JSON/base64 обрабатываются в памяти, поэтому пиковая память выше размера архива; большие библиотеки требуют будущего потокового формата. Ожидание readonly-снимка ограничено 15 секундами; при занятом/заблокированном хранилище повторите операцию после завершения активности. Частичный результат при отказе/квоте сохраняется в отдельных `langkraft-sqlite-recovered-*` / `langkraft-audio-recovered-*`, ссылка не выдаётся. Автоматической уборки этих следов пока нет. Повторные копии/экспорты занимают дополнительное место.

Эти профили изолируют данные и блокировки, но остаются внутри одного origin и общей browser quota. Это не граница безопасности между пользователями. Архив содержит личную библиотеку/SRS; храните его как резервную копию. Исходные legacy, partial, unlinked и неизвестные записи не удаляются; в новый профиль переносится только проверенное связанное аудио.

## Проверка утилиты

```powershell
python -W error::ResourceWarning -m unittest discover -s tools/recovery/tests -v
```

Тесты проверяют read-only аудит, активного WAL-писателя, SRS/очередь/общие audio, очистку сессии только в копии, недоступные пути, нестабильный файл, смену версии схемы во время snapshot, отказ записи и запрет перезаписи назначения. Они подключены к JVM job CI отдельно от Gradle-тестов.

Web: `npm test` в `tools/web-storage-tests` запускает storage и recovery Chromium-сценарии. `npm run test:app` проверяет страницу, загрузку/импорт архива и полный Compose-клиент на копии реальной schema v3 библиотеки. Эти команды входят в Web job CI; development/production сборки проверяются отдельно.
