# Диспетчеры backend

NEXT-2 переносит блокирующие операции из coroutine обработки HTTP, сохраняя существующие
синхронные репозитории и границы транзакций Exposed.

| Операция | Где выполняется |
| --- | --- |
| Auth: поиск пользователя и создание учётной записи | BackendWork.jdbc → Dispatchers.IO |
| Проверка существования AccountId при JWT-аутентификации | BackendWork.jdbc → Dispatchers.IO |
| Sync: проверка пользователя и целый synchronize | BackendWork.jdbc → Dispatchers.IO |
| HTTP admission импорта и чтение статуса job | BackendWork.jdbc → Dispatchers.IO |
| BCrypt hash и verify | Общий BackendWork.password → ограниченный view Dispatchers.Default |

AuthService использует suspend-методы register/login. Диспетчеры переключаются вокруг
целого синхронного вызова; внутри Exposed-транзакции новых suspension points нет.
SQL-инварианты, insertIgnore при конкурентной регистрации и revision-aware sync сохранены.
HTTP DTO и клиент не меняются.

## Параллельность BCrypt

```properties
LANGKRAFT_MAX_CONCURRENT_HASHES=2
```

Настройка соответствует `auth.max_concurrent_hashes`, допускает 1–16; по умолчанию 2.
Неверная настройка останавливает bootstrap до открытия БД и HTTP-клиентов.
Один BackendWork создаётся в Koin для приложения; hash регистрации и verify входа
используют один ограниченный dispatcher view. Лимит относится к реально выполняющимся
синхронным BCrypt-операциям, а не к числу ожидающих HTTP-запросов.

Dispatcher view использует общий CPU-пул coroutines и не создаёт собственного executor,
который пришлось бы закрывать. JDBC остаётся на IO и не занимает BCrypt-слоты.
Rate limit и ограничение числа ожидающих запросов относятся к публичному режиму NEXT-5.

## Отмена и результат записи

Перед началом каждой операции проверяется отмена. Ожидающий BCrypt запрос можно отменить,
не запуская вычисление. Отмена во время хэширования не освобождает слот раньше окончания
самого синхронного вычисления. Его результат не передаётся отменённому запросу;
регистрация не переходит к INSERT после отмены ожидания/хэширования.

Начавшийся JDBC-вызов не прерывается насильно. Он завершает транзакцию целиком либо
откатывает её при ошибке. Отмена пробрасывается вызывающей coroutine, но запись могла
уже зафиксироваться. Это не означает частичную запись: повтор регистрации вернёт
конфликт существующего email, а повтор sync использует прежние revision/idempotency правила.
В HTTP admission принятый job по-прежнему переживает закрытие POST.

Миграции и recovery при запуске выполняются до приёма HTTP, а ingestion workers уже
используют IO scope. Управление завершением workers/resources остаётся NEXT-4.

## Проверки

```powershell
.\gradlew.bat :backend:test
```

Восемь новых тестов проверяют фактическую параллельность, доступность caller/IO при
занятом BCrypt-диспетчере, отмену выполняющегося и ожидающего задания, отсутствие учётной
записи при отмене регистрации, гонку email и настоящий BCrypt verify, атомарный rollback
при нарушении владения, завершённый sync после отмены и безопасный повтор.
Полный backend-прогон также проверяет настоящие HTTP auth/JWT/sync/ingestion маршруты.
Нагрузочные метрики latency/throughput этим спринтом не измерялись.
