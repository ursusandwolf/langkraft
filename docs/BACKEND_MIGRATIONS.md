# Миграции backend SQLite

`BackendDatabase.open` проверяет и обновляет серверную `storage.data_dir/langkraft.db`
до создания HTTP-клиентов и запуска ingestion workers. Backend больше не вызывает
`SchemaUtils.createMissingTablesAndColumns` при старте. Клиентские SQLDelight-миграции
остаются отдельным механизмом.

## Версии

Неизменяемые SQL-файлы находятся в `backend/src/main/resources/db/migrations`:

| Версия | Изменение |
| --- | --- |
| 1 | users, уникальный email, vocabulary_sync с владельцем и основными SRS-полями |
| 2 | lapse_count, tags и persistent ingestion_jobs |
| 3 | server_updated, deleted и однократное заполнение нулевых серверных курсоров |

`backend_schema_history` хранит номер, имя, SHA-256 SQL и время выполнения.
Переводы строк нормализованы в LF для переноса БД между Windows и Linux.
Новые изменения добавляются следующими версиями; применённые файлы не редактируются.
Пропуск версии, несовпадение checksum, повреждённая история или более новая версия
останавливают запуск. При текущей версии повторный запуск не выполняет DDL и не
перезаписывает курсоры.

## Существующие базы без истории

Поддерживаются старые схемы из истории проекта: users/vocabulary_sync без lapse_count/tags,
вариант с этими полями, вариант с ingestion_jobs и текущая схема с server_updated/deleted.
До любых изменений проверяются состав таблиц и столбцов, SQLite affinity, nullable/PK,
уникальность email, ссылка владельца, `quick_check` и `foreign_key_check`.
Неизвестные таблицы/столбцы, отсутствующие обязательные поля или осиротевшие владельцы
останавливают запуск. Произвольная повреждённая БД автоматически не ремонтируется.

После проверки существующие известные столбцы сохраняются, недостающие добавляются,
все три версии фиксируются в одной транзакции. Сохранённые ненулевые курсоры и tombstones
не изменяются. Свежая БД проходит те же SQL-версии без резервной копии.

## Backup и откат

Перед изменением существующей БД создаётся SQLite-снимок через `VACUUM INTO`:

```text
langkraft.db.before-backend-schema-3-<UUID>.bak
```

Он включает committed WAL-данные. Каждый повтор обновления создаёт новый снимок;
существующие копии, включая старые `.before-sync-v2.bak`, сохраняются. Автоматической
retention резервных копий нет. Ошибка снимка останавливает миграцию; неуспешную,
возможно неполную копию нельзя использовать без проверки целостности.

Все DDL, backfill и записи истории выполняются в одной `BEGIN IMMEDIATE` транзакции.
Ошибка откатывает их целиком. `<db>.migration.lock` защищает backup и миграции от
одновременного bootstrap другого процесса; файл остаётся после освобождения lock.
Этот lock не координирует работающие старые версии приложения. Перед обновлением
остановите все backend-процессы, использующие каталог данных; один каталог рассчитан
на один работающий backend.

Для ручного отката остановите backend, проверьте копию через SQLite `PRAGMA quick_check`,
сохраните текущую БД вместе с её WAL/SHM отдельно, затем восстановите снимок и запустите
совместимую версию кода. Старые WAL/SHM нельзя оставлять рядом с восстановленным файлом.
Автоматического downgrade нет. Снимок восстанавливает только БД, не файлы media.

## Проверки

```powershell
.\gradlew.bat :backend:test --tests com.langkraft.backend.db.BackendDatabaseTest
```

Тесты используют изолированные временные БД и SQL fixture ранней схемы. Проверяются
новая БД/restart, известные legacy-варианты, сохранение данных и backup, WAL и пути
с апострофом, откат после ошибки и повтор, отказ для неизвестной схемы/истории/версии,
осиротевших владельцев и конкурирующего bootstrap. Общий `:backend:test` также проверяет
auth, sync, ingestion и media с новым bootstrap.
