## Состав архива

Снимок исходников: коммит `397d007` (`fix: bound imports and preserve persisted subtitle order`). README дополнен после этого коммита: требования к окружению, зависимости, запуск и диагностика. Полный hash исходного коммита, дополнения документации и контрольные суммы файлов указаны в `ARCHIVE_MANIFEST.json`. Файлы проекта находятся относительно корневой папки `langkraft/` в ZIP.

Включены рабочие исходники backend/shared/webApp, схема SQLDelight и миграция, Gradle-конфигурация, Wrapper, lock-файл Web-зависимостей, CI и актуальная документация. `gradle-wrapper.jar` — необходимая часть Wrapper, а не результат сборки приложения.

**Тесты исключены по запросу владельца.** Также исключены тестовые fixtures, инструменты браузерных тестов, Karma-конфигурация, архивная документация, `.git`, кэши, зависимости, сборки, скачанные медиа и локальные настройки. Ссылки README, CI и документов на исключённые тестовые файлы относятся к полному репозиторию. Не считай их отсутствие в ZIP дефектом проекта. Тестовую реализацию и полноту покрытия по этому архиву оценить нельзя.

## Контекст

Langkraft — приложение для изучения немецкого: YouTube URL → извлечение Opus, немецких субтитров и метаданных → локальное сохранение → прослушивание с синхронными субтитрами → перевод и сохранение слова.

- Приоритет — Web. Android включается через `-PenableAndroid=true` и отложен до финального этапа; Android-сборка не подтверждена.
- Kotlin Multiplatform, Compose Multiplatform, Ktor, SQLDelight; версии смотри в Gradle-файлах.
- Backend вызывает yt-dlp отдельными аргументами без shell. Для настоящего импорта нужны Node.js 22+, yt-dlp и FFmpeg.
- Web хранит SQLite/WASM в worker с IndexedDB VFS; аудио — отдельно в IndexedDB, частями.
- `DatabaseAccess` сериализует доступ репозиториев к одному соединению. `PlayerViewModel` владеет дочерней coroutine scope и управляет платформенным плеером.
- Перевод явно демонстрационный. Реальный Gemini, полноценное SRS-обучение, PWA и авторизация остаются в roadmap.

Начни с `README.md`, `docs/PROJECT_CONTEXT.md`, `docs/DATA_LAYER.md`, `docs/SUBTITLES.md`, затем прочитай исходники. Сначала сформируй собственные выводы; после этого сопоставь их с `docs/CODE_REVIEW_2026-10-21.md`. Последний документ содержит первоначальные находки и отдельный раздел с последующими исправлениями: не объявляй исправленную находку актуальной без проверки текущего кода.

## Приоритетные проверки

1. **Импорт и процессы:** проверка URL, обработка метаданных и субтитров, таймаут, disconnect, завершение дочерних процессов, удаление временных файлов. Лимит `MAX_CONCURRENT_IMPORTS` по умолчанию 2; лишний запрос должен сразу получать 503 без очереди. Слот должен освобождаться после успеха, ошибки и отмены, включая отмену при переключении dispatcher.
2. **Данные и миграция:** атомарность content/subtitles, внешние ключи, сохранность ссылок слов и SRS. Схема 2 добавляет `SubtitleLine.ordinal`; одинаковые начала реплик должны сохранять порядок входного списка при обеих выборках, обновлении и повторном открытии БД. Миграция старых реплик задаёт ordinal 0: для них предусмотрен единый порядок по ID, поскольку исходный порядок не был сохранён.
3. **Согласованность SQLite и аудиохранилища:** ошибки/отмена до и после публикации аудио, сбой финального сохранения ссылки, квота, неполные загрузки и непривязанные объекты.
4. **Web worker и IndexedDB:** очередь сообщений, транзакции и rollback, закрытие/таймаут worker, жизненный цикл Blob URL, открытие нескольких вкладок и обновление наблюдаемых списков.
5. **Плеер и UI:** гонки загрузки/перевода/сохранения, устаревшие ответы, восстановление состояния после ошибки, retry, seek, освобождение scope и аудиоресурсов, доступность ключевых действий.
6. **Контракты и сборка:** HTTP-ответы, разрешение media URL, Range, единый origin/proxy, разделение платформ, соответствие документации фактическому поведению.

Известные открытые направления: лимит параллельности ещё не ограничивает размер/длительность загрузок и общий объём downloads; нужна политика хранения. Возможные непривязанные аудиообъекты и межвкладочные уведомления требуют отдельной проверки. Отделяй эти ограничения от новых находок и оценивай их с учётом доверенного локального запуска либо публичного размещения.

## Правила проверки

- Каждую находку обоснуй сценарием, цепочкой вызовов и точным участком кода. Разделяй воспроизведённое поведение, вывод из статического анализа и гипотезу.
- Сначала корректность и потеря данных, затем безопасность/ресурсы, затем дизайн. Не предлагай переписывать архитектуру без связи с конкретным дефектом.
- Не выдавай запланированные возможности за регрессии MVP. Для UI и Android явно укажи границы проверки.
- Если запускаешь команды, запиши их результаты. Не утверждай, что тесты прошли, если их нет в архиве. Проверки полного репозитория до упаковки: 67 JVM-тестов, 24 Kotlin-теста в Chromium, три сценария хранилища, development/production-сценарии приложения и миграции. Это сведения автора, а не твои независимые результаты. Успешный hosted CI после исправления зависимостей ещё не подтверждён.
- Для статического ревью внешние сервисы и ключи не нужны. Без отдельного запроса не обращайся к YouTube, не развёртывай приложение и не публикуй результаты.

При доступном JDK 21 и Node.js 22+ можно проверить компиляцию без исключённых тестов (на Windows замени `bash ./gradlew` на `.\gradlew.bat`):

```shell
bash ./gradlew :shared:compileKotlinDesktop :backend:classes :shared:compileKotlinJs
bash ./gradlew :webApp:jsBrowserDevelopmentWebpack
bash ./gradlew :webApp:jsBrowserDistribution
```

Команды сборки требуют доступа к репозиториям зависимостей. Development и production запускай отдельными вызовами Gradle: Kotlin 1.9 использует общий каталог compileSync. Полный CI из этого ZIP воспроизвести нельзя, поскольку тестовые исходники и инструменты исключены.
