База ревью: `5a1e60ae90179376db99204ff9cff6a4d4ebf092` и локальное исправление npm/webpack из текущего рабочего дерева. Проверены backend, общий слой данных, Web storage/worker, плеер, связывание Web UI, тесты и конфигурация сборки/CI. Android просмотрен статически; его сборка отложена согласно roadmap.

## 1. P1 / Major: каждый параллельный запрос запускает отдельную загрузку без общего лимита

**Где:** [YouTubeIngestionService.kt:34](../backend/src/main/kotlin/com/langkraft/backend/YouTubeIngestionService.kt#L34), [Application.kt:37](../backend/src/main/kotlin/com/langkraft/backend/Application.kt#L37).

Каждый `POST /api/ingest` сразу запускает yt-dlp. Ограничение кнопки в браузере действует только в одной вкладке; сервер не ограничивает число процессов, размер файлов или длительность видео. Таймаут процесса в десять минут ограничивает время одной операции, но не совокупную нагрузку. Успешные импорты остаются в downloads без политики удаления. Несколько клиентов или повторяющийся скрипт могут исчерпать CPU/диск, затронув остальные запросы.

**Предложение:** ограничить одновременно работающие импорты и очередь ожидания, отклонять перегрузку явным HTTP-ответом; задать бюджет размера/длительности и политику хранения успешных файлов. Для доверенного локального запуска риск ниже; до открытия сервиса внешним пользователям это блокирующее замечание.

**Проверка исправления:** удержать N операций тестовым runner, послать N+1 запрос и проверить ограниченное число запущенных runner, ответ перегрузки и освобождение слота после ошибки/отмены. Отдельно проверить соблюдение бюджета хранения. Вывод основан на статическом анализе; нагрузочная проверка не запускалась.

## 2. P2 / Major: ошибка финального сохранения оставляет аудио без ссылки

**Где:** [IngestContentUseCase.kt:22](../shared/src/commonMain/kotlin/com/langkraft/domain/usecase/IngestContentUseCase.kt#L22), [IngestContentUseCase.kt:26](../shared/src/commonMain/kotlin/com/langkraft/domain/usecase/IngestContentUseCase.kt#L26).

`downloadAudio` публикует завершённый файл/запись IndexedDB до второго `saveContent`. Если этот save падает, например из-за квоты хранилища, use case возвращает ошибку, а SQLite сохраняет первоначальный контент с `localAudioPath = null`. Уже опубликованное аудио остаётся недоступным из библиотеки. Отмена после завершения download и до фиксации ссылки даёт тот же сценарий. `AudioStorage` предоставляет только `store`, поэтому use case не может компенсировать такой сбой; очистка внутри storage работает лишь до возврата из `store`.

**Предложение:** предусмотреть удаление опубликованного аудио при неуспешной привязке к контенту либо протокол подготовки/подтверждения с последующей уборкой непривязанных объектов. Сохранение корректных удалённых метаданных при сбое скачивания уже является намеренным поведением и менять его не требуется.

**Проверка исправления:** успешная загрузка, отказ именно второго save, затем проверка отсутствия непривязанного аудио и сохранности удалённых метаданных. Повторить с отменой на границе download/save. Сейчас тесты покрывают отказ самого скачивания, но не этот переход. Вывод основан на последовательности вызовов и контрактах storage.

## 3. P2: стабильный порядок реплик теряется после сохранения

**Где:** [AppDatabase.sq:55](../shared/src/commonMain/sqldelight/com/langkraft/db/AppDatabase.sq#L55), [AppDatabase.sq:66](../shared/src/commonMain/sqldelight/com/langkraft/db/AppDatabase.sq#L66).

Парсер и документация обещают сохранять исходный порядок реплик с одинаковым `startMs`. Однако `selectLibrary` сортирует такие реплики по случайному UUID, а `selectSubtitlesForContent` вообще не определяет вторичный порядок. Исходный номер реплики в схеме не хранится. Поэтому после сохранения порядок расходится с результатом парсера; библиотека и плеер могут получать разные списки. Это влияет и на выбор первой активной реплики для автопрокрутки при совпадающем начале.

**Воспроизведение выполнено:** в SQLite созданы две реплики с `startMs = 0` в порядке `z-first`, `a-second`. Использованы реальные запросы из `AppDatabase.sq`: библиотека вернула `a-second`, `z-first`, чтение по content ID — `z-first`, `a-second`. Тест парсера на стабильные совпадения начала не проходит через репозиторий и этот дефект не обнаруживает.

**Предложение:** сохранять порядковый номер реплики и одинаково сортировать оба запроса по `startMs, ordinal`; предусмотреть миграцию существующей базы.

**Проверка исправления:** импорт → сохранение → обе выборки → закрытие и повторное открытие базы; порядок совпадающих начал должен сохраняться на всех этапах.

## 4. P2: библиотека не обновляется после импорта в другой вкладке

**Где:** [BrowserSqlDriver.kt:98](../shared/src/jsMain/kotlin/com/langkraft/data/database/BrowserSqlDriver.kt#L98), [Main.kt:114](../webApp/src/jsMain/kotlin/com/langkraft/web/Main.kt#L114).

Каждая вкладка создаёт свой driver и worker для одного постоянного хранилища. `notifyListeners` уведомляет только listeners текущего экземпляра. Между вкладками нет уведомления об изменении базы, а библиотека подписана на SQLDelight Flow без периодического обновления. При импорте в одной вкладке уже открытая библиотека другой останется со старым списком до пересоздания подписки/перезагрузки. Минутный refresh слов частично скрывает это для словаря, но у библиотеки его нет.

**Предложение:** уведомлять другие вкладки после успешного commit через межвкладочный канал и перечитывать затронутые запросы либо явно ограничить приложение одной активной вкладкой. Отдельно проверить одновременные записи через разные worker: mutex `DatabaseAccess` защищает только один экземпляр соединения.

**Проверка исправления:** открыть две страницы одного browser context, подписать библиотеку в обеих, импортировать в первой и дождаться обновления во второй без reload. Это замечание основано на статическом анализе механизма уведомлений; браузерный сценарий с двумя вкладками в этом ревью не запускался.

## Что уже сделано хорошо

- yt-dlp запускается отдельными аргументами без shell; вход ограничен HTTPS YouTube URL.
- Сохранение контента и субтитров транзакционное; обновления не используют разрушительный REPLACE и сохраняют связи слов/SRS.
- Ошибки субтитров отклоняют весь импорт; отмена пробрасывается и завершает дочерние процессы.
- Плеер защищён от устаревших результатов перевода и освобождает собственные ресурсы.
- Есть проверки с настоящими SQLite, worker/WASM и IndexedDB, а не только моки.
