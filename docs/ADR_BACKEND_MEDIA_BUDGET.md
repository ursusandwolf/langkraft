# Backend media budget — REL-14

## Контекст и выбор

Retention ограничивает срок хранения, но не пик диска. Проверка текущего размера без резервирования позволяет параллельным импортам использовать одно свободное место. Оценки yt-dlp не включают все промежуточные файлы; неизвестный размер не является доказательством малого файла.

Рассмотрены три варианта: только оценки metadata (дёшево, но ненадёжно); фиксированный резерв на импорт и контроль файлов (выбран для текущего backend); квота/изоляция на уровне ОС (нужна для строгой границы, требует настройки окружения). Фиксированный резерв консервативен: даже маленький queued job временно занимает полный max_import_bytes, зато не делит его с другим импортом.

## Конфигурация

| Параметр | Env | Default |
| --- | --- | --- |
| storage.max_import_bytes | LANGKRAFT_MAX_IMPORT_BYTES | 0: byte-limit выключен |
| storage.max_total_bytes | LANGKRAFT_MAX_TOTAL_BYTES | 0: общий бюджет выключен |
| storage.budget_check_interval_ms | LANGKRAFT_BUDGET_CHECK_INTERVAL_MS | 200, допустимо 10–60000 |
| ingestion.max_duration_seconds | LANGKRAFT_MAX_DURATION_SECONDS | 14400, допустимо 1–86400 |

Общий бюджет требует положительный max_import_bytes ≤ max_total_bytes. Некорректная конфигурация отклоняется при старте. Можно включить только per-import limit. Один процесс backend владеет downloads_dir/БД, как в [retention ADR](ADR_BACKEND_MEDIA_RETENTION.md).

## Admission и учёт

BackendMediaStorage под тем же monitor, что управляет leases/retention, регистрирует резерв до создания job в БД. Учёт равен сумме фактических размеров файлов вне активных импортов плюс max(резерв, фактические байты) каждого активного/queued job. Регулярные legacy/unknown файлы тоже считаются; symlink не обходятся. Считаются логические размеры файлов, не выделенные блоки файловой системы. Исчезновение временного файла при сканировании допустимо; другие ошибки чтения не отключают контроль.

Свободное место файловой системы дополнительно сравнивается с суммой ещё не записанных частей резервов. Это предварительная проверка: внешние процессы могут занять диск позже, ошибка записи остаётся штатным отказом импорта.

Если места не хватает, выполняется только уже разрешённая retention-уборка, затем повторная проверка. Неистёкшее/legacy/читаемое медиа не вытесняется ради нового импорта. Отказ даёт HTTP 503 с Retry-After: 5 **до записи job в БД**. Semaphore/очередь остаются отдельным лимитом. Ошибка admission освобождает слот и резерв.

## Проверки в работе

Metadata должна содержать конечную положительную длительность в лимите; is_live=true отклоняется. Если filesize/filesize_approx известны и превышают per-import budget, скачивание не запускается. Неизвестный размер разрешён при известной допустимой длительности и контролируется по фактическим байтам.

Обрабатывающая корутина и монитор размера находятся в coroutineScope. Превышение отменяет обработку; scope ждёт завершения и reap внешних процессов до очистки каталога и освобождения lease. Job получает ERROR с сообщением о byte-limit, worker продолжает обслуживать очередь.

Все job-процессы используют executeIn: логи metadata/yt-dlp/ffmpeg создаются в каталоге job; PCM waveform также перенесён туда. В бюджет входят исходный media, .part, конвертируемый MP3, субтитры, логи, PCM и протокольная метка. Runner проверяет callback бюджета во время работы (каждые 100 мс) и после завершения **до удаления лога**; верхний монитор дополнительно работает с budget_check_interval_ms. Проверки после download/waveform и перед publish ловят короткие превышения, ещё присутствующие при завершении стадии. Waveform не превращает MediaLimitException в нулевой fallback.

Лог процесса ограничен 2 МиБ и проверяется во время работы, а не только после exit. Runner отслеживает известных потомков, завершает их даже после выхода родителя и закрывает redirected file handles до удаления логов. Как и прежде, процессы не должны самостоятельно daemonize/отрываться от дерева до обнаружения; полная изоляция требует средств ОС.

Периодический монитор допускает превышение между проверками. Это **не жёсткая дисковая квота**: для строгой границы нужна квота/изоляция файловой системы. Таймауты yt-dlp 600 с и ffmpeg 120 с сохраняются.

## Завершение и restart

До публикации проверяется фактический размер с промежуточными файлами. После разбора субтитров/waveform retainAudio оставляет MP3 и ownership marker; API сохраняет распарсенные subtitles/waveform. Publish повторно проверяет бюджет, выполняет callback READY и заменяет резерв фактическим размером готового каталога. Ошибка/отмена снимает резерв после остановки процессов и попытки очистки. Если удалить файлы не удалось, они продолжают учитываться по фактическому размеру; логическое освобождение резерва не означает освобождения места.

После restart нет унаследованных in-memory резервов: interrupted jobs переходят в ERROR, оставшиеся pending/ready/legacy файлы учитываются заново. Удаление подчиняется retention-протоколу; выключенный TTL не означает игнорирования оставшихся байтов.

## Проверки

MediaBudgetTest: конкурентное резервирование, отсутствие двойного учёта active bytes, переход к actual bytes при публикации, legacy, частичный отказ очистки, .part/log byte-limit, pruning и валидация config. IngestionBudgetTest: 503 до persistence, освобождение при shutdown, metadata preflight, growing download/отмена/повтор и waveform quota. ProcessRunnerTest: настоящее дерево Java-процессов, quota kill/reap, выход родителя с живым потомком и остановка при росте лога.
